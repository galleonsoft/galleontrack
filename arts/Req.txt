## GalleonTrack Offline-First Callyzer-Style Call Tracking, Lead Management & Analytics Application

## 1. Project Overview

Act as a senior Flutter developer, mobile application architect, UI/UX designer, Android native developer, database engineer, and QA specialist.

Develop a complete, production-quality Flutter application inspired by Callyzer, with comprehensive call tracking, lead management, employee management, analytics, reporting, and local call recording management.

The application must be **fully offline-first, with all business data stored locally using Hive CE**.

The only network functionality permitted is one optional, user-initiated API endpoint that exports selected local database data and sends it to a configured server.

There must be no other API communication, cloud dependency, remote database, online authentication, CRM integration API, or automatic data synchronization.

### Core requirements

- Flutter and Dart
- Android-first development
- Hive CE as the primary and only business database
- Riverpod for state management
- Clean architecture
- Material Design 3
- Fully functional offline operation
- Local analytics and reporting
- Local PDF, CSV, and Excel-compatible exports
- Local notifications and reminders
- Supported local call-log access
- Local recording management
- Employee and lead management
- One optional export API endpoint
- No mandatory internet connection

The app must remain fully functional when the device has no internet connection, including first launch, workspace creation, data entry, searching, analytics, reporting, and local file export.

Do not build a UI-only prototype. Implement actual business logic, database persistence, validation, filtering, reporting, and error handling.

## 2. Strict Network and API Restrictions

This section is mandatory and overrides any conflicting implementation suggestion elsewhere in this prompt.

### The application may use only one API endpoint

The only permitted network endpoint is:

`POST /api/v1/database-export`

The endpoint is intended exclusively for sending user-selected local data exports to a server.

The server URL must be configurable in application settings.

The API must not be required to launch or use the application.

### The only permitted network workflow

1. The user opens Settings.
2. The user opens Database Export to Server.
3. The app displays locally available data categories.
4. The user selects the data to export.
5. The app displays the selected record counts and file sizes where available.
6. The user reviews the destination server URL.
7. The user explicitly confirms the export.
8. The app prepares an export package locally.
9. The app sends the package using the single permitted POST endpoint.
10. The app displays the confirmed result or a clear error.
11. The app stores the local export history.

### Prohibited network functionality

Do not implement:

- Cloud database integration
- Firebase
- Supabase
- Remote authentication
- API login or token refresh endpoints
- API-based lead management
- Remote employee management
- CRM APIs
- Zoho integration
- LeadSquared integration
- Google Sheets integration
- Webhooks
- Third-party data synchronization
- Automatic background uploads
- Automatic cloud backups
- Remote configuration fetching
- Server-side analytics fetching
- Remote report generation
- Server-side search
- Remote call-log synchronization
- Automatic upload when internet becomes available
- Any additional API endpoint
- Any background network task for business data

Do not add network calls simply to check connectivity or server status.

The only network request must be the user-initiated database export request.

Do not add a server health endpoint or authentication endpoint. If an export connection test is required, use the same permitted export endpoint with an explicitly documented test operation in its request contract, or omit the test.

### Network isolation

The app's normal repository layer must not depend on a remote service.

Every business feature must work through local repositories backed by Hive CE.

The API export service must be isolated from the rest of the application. It must receive a locally generated export package and send it only after explicit confirmation.

No background job, listener, connectivity event, or scheduled task may initiate an upload.

## 19. The Single Permitted Database Export API

Implement one isolated service named `DatabaseExportApiService`.

Its sole purpose is to send user-selected local data to the configured server.

### Endpoint

`POST /api/v1/database-export`

Use a configurable base URL.

The endpoint contract should be documented, but no additional endpoint may be created or called by the Flutter application.

### Export selection

Allow users to select:

- All permitted database records
- Call records
- Leads
- Contacts
- Employees
- Teams
- Follow-ups
- Lead status history
- Excluded numbers
- Recording metadata
- Selected recording files
- Selected date ranges
- Selected employees or teams

Do not upload data types the user has not selected.

### Export package

Generate a versioned archive locally.

Suggested structure:

```text
database_export.zip
├── manifest.json
├── app_settings.json
├── employees.json
├── teams.json
├── calls.json
├── leads.json
├── contacts.json
├── follow_ups.json
├── lead_statuses.json
├── excluded_numbers.json
├── recording_metadata.json
└── recordings/
```

Include only selected data.

The manifest should contain:

- Export ID
- Export schema version
- Application version
- Export timestamp
- Selected data categories
- Record counts
- File inventory
- Optional checksums

Do not include credentials, PINs, access tokens, private keys, or unnecessary device identifiers.

Use stable IDs to preserve relationships among exported records.

Validate the archive before sending it.

### API request

Send the generated archive as a multipart upload or another explicitly documented request format using the single POST endpoint.

Include the export manifest and necessary request metadata.

Do not invent the server's response structure. Define and document the expected response contract for the backend developer.

### API response

Handle:

- Successful receipt
- Rejected export
- Invalid request
- Unauthorized response if the server requires authorization
- Request timeout
- Connection failure
- Server error
- Malformed response
- Upload cancellation

A successful HTTP response must be interpreted according to the documented server response contract.

Do not treat a timeout as proof that the server did not receive the package.

### User interface

Create a Database Export to Server screen with:

- Server URL
- Selected categories
- Selected record counts
- Archive size
- Include recordings toggle
- Export preview
- Privacy warning
- Confirmation dialog
- Upload progress
- Cancel action
- Final status
- Local export history

Require explicit user confirmation before sending the archive.

### Export history

Store locally:

- Export ID
- Export timestamp
- Destination URL
- Selected categories
- Record counts
- Package size
- Completion status
- Sanitized error information

Do not store sensitive credentials in export history.

### API security

- Prefer HTTPS.
- Never hardcode production secrets.
- Do not embed a privileged server API key in the app.
- If authentication is required, use a securely configured, least-privilege mechanism supported by the server.
- Do not implement separate login or token-refresh API endpoints.
- Do not log exported customer details or credentials.
- Warn the user before transmitting personal data.
- Keep local files unless the user explicitly deletes them.

### Offline behavior

If the device has no internet connection, all app features must continue working.

The export screen should display that sending is currently unavailable.

Do not initiate retries automatically when connectivity returns.

The user must initiate another export attempt.

### No automatic background export

Never upload a database automatically:

- On app launch
- On app close
- When a lead is created
- When a call is imported
- When a recording is discovered
- When internet connectivity changes
- On a scheduled background task

The only upload is the explicit user-initiated export workflow.

## 28. Final Acceptance Criteria

The application is complete only when all these conditions are met:

### Offline functionality
- The app launches without internet.
- No online account is required.
- Leads, employees, teams, notes, and follow-ups persist locally.
- Call history imports work where supported.
- Search and filtering work offline.
- Analytics use local data.
- PDF, CSV, and local backup work offline.
- Local notifications work where supported.
- Restarting the app preserves saved records.

### Data integrity
- Hive CE is the only primary business database.
- Database migrations are versioned.
- Repeated call imports do not create uncontrolled duplicates.
- Relationships remain valid.
- Backups can be validated and restored.
- Export archives preserve selected records and relationships.

### API restrictions
- Exactly one API endpoint is used: `POST /api/v1/database-export`.
- The API is optional.
- No API is required for app startup or ordinary features.
- No other remote services are integrated.
- No automatic upload occurs.
- The user must explicitly select data and confirm each export.
- Failed exports do not cause local data loss.
- No automatic retry occurs when connectivity returns.
- Local backup does not call the API.

### Recording functionality
- Supported local recordings can be imported and played.
- Missing files are handled gracefully.
- Local recordings are preserved by default.
- Uploading recordings requires explicit selection and confirmation.
- Unsupported telephone recording functionality is disclosed.

### Code quality
- The project builds with documented commands.
- Tests cover the core business logic.
- No critical feature is a placeholder.
- UI, repositories, database services, and API export code are separated.
- Sensitive information is protected.
- No unexpected network traffic is initiated by the app.
